# Agent Guidelines for hoozi_radar

## Project Overview

This repository is the frontend web radar for **HOOZi**.

Historically, this project targeted the legacy **HOOZi 2.0** data stream. The current development goal is to migrate the frontend so it fully supports the **HOOZi 3.0** Lua-driven web radar data stream produced by `web_radar.lua`.

The HOOZi 3.0 Lua script runs inside the HOOZi 3.0 client/backend environment. It processes HOOZi runtime data, sends messages to the server side, and provides data to this web radar frontend.

## Repository Layout

Core frontend files:

* `/index.html` is the static page entry.
* `/app.js` currently contains the main frontend logic, including data reception, state transformation, rendering behavior, UI interactions, and map/radar logic.
* `/input.css` contains the Tailwind CSS v4 import.
* `/styles.css` is generated by the Tailwind CLI based on Tailwind class usage in `index.html` and related frontend files.
* `/static/` contains local fallback map/rendering assets.

Reference files for HOOZi 3.0 Lua data stream:

* `/references/hapex3-lua-script-factory/README.md`
* `/references/hapex3-lua-script-factory/README_CN.md`
* `/references/hapex3-lua-script-factory/AGENTS.md`
* `/references/hapex3-lua-script-factory/references/api-reference.md`
* `/references/hapex3-lua-script-factory/references/examples.md`
* `/references/hapex3-lua-script-factory/references/guide.md`
* `/references/hapex3-lua-script-factory/scripts/web_radar.lua`

Project-owned protocol documentation:

* `/docs/protocol/hoozi3-web-radar-protocol.md`

The `references/hapex3-lua-script-factory/` directory is a read-only reference snapshot copied from the local HOOZi 3.0 Lua script factory project. Do not modify files under this directory unless the user explicitly asks to update the reference snapshot.

## Required Reading for HOOZi 3.0 Migration Tasks

Before modifying protocol parsing, message handling, field mapping, entity rendering, radar behavior, or HOOZi 3.0 compatibility logic, read the following files:

1. `/references/hapex3-lua-script-factory/AGENTS.md`
2. `/references/hapex3-lua-script-factory/README.md`
3. `/references/hapex3-lua-script-factory/scripts/web_radar.lua`
4. `/references/hapex3-lua-script-factory/references/api-reference.md`

Read these additional files when needed:

* `/references/hapex3-lua-script-factory/references/guide.md` for lifecycle, timing, structure, and cross-script behavior.
* `/references/hapex3-lua-script-factory/references/examples.md` for complete Lua usage examples.

Important: Codex may not automatically load nested `AGENTS.md` files under `references/`. For HOOZi 3.0 migration work, explicitly inspect the reference files above before implementing changes.

## Source of Truth Rules

When old HOOZi 2.0 frontend behavior conflicts with HOOZi 3.0 Lua output, use the following precedence:

1. `references/hapex3-lua-script-factory/scripts/web_radar.lua`
2. `references/hapex3-lua-script-factory/references/api-reference.md`
3. `references/hapex3-lua-script-factory/references/guide.md`
4. `references/hapex3-lua-script-factory/references/examples.md`
5. Existing HOOZi 2.0 frontend behavior

Do not invent field meanings.

Do not assume that HOOZi 2.0 field names, units, coordinate systems, entity categories, status flags, or rendering semantics still apply to HOOZi 3.0.

If a field exists in the old frontend but not in `web_radar.lua`, mark it as legacy and do not preserve it unless there is a verified HOOZi 3.0 equivalent.

If `web_radar.lua` provides a new field, implement the corresponding frontend behavior when its meaning can be verified from the Lua script or API references.

If a field meaning cannot be verified, document the uncertainty in `/docs/protocol/hoozi3-web-radar-protocol.md` and avoid speculative behavior.

## HOOZi 3.0 Migration Requirements

The migration must make the frontend fully compatible with the data stream produced by `web_radar.lua`.

The implementation should include:

* Message reception and parsing for the HOOZi 3.0 data stream.
* Field mapping from HOOZi 3.0 Lua output to frontend state.
* Removal or isolation of obsolete HOOZi 2.0-only assumptions.
* Support for all verified new fields provided by `web_radar.lua`.
* Correct rendering behavior for players, teams, local player state, loot, projectiles, map state, status flags, and other supported entities when those fields are present and documented.
* A clear protocol document at `/docs/protocol/hoozi3-web-radar-protocol.md`.

## JavaScript Architecture Requirements

The old project may contain a large monolithic `/app.js`. For the HOOZi 3.0 version, split the frontend code into maintainable native ES module files.

Use native browser ES modules. Do not introduce a bundler unless the user explicitly approves it.

Recommended module structure:

* `/src/main.js` — application bootstrap and high-level wiring.
* `/src/config.js` — constants, CDN paths, feature flags, default settings.
* `/src/i18n.js` — Simplified Chinese, Traditional Chinese, and English translations.
* `/src/protocol/hoozi3.js` — HOOZi 3.0 message parsing, validation, normalization, and field mapping.
* `/src/state/store.js` — frontend state container and state update helpers.
* `/src/render/radar.js` — radar/map rendering logic.
* `/src/render/entities.js` — entity-specific rendering helpers.
* `/src/ui/controls.js` — UI controls, toggles, panels, and event handlers.
* `/src/assets/maps.js` — map/static asset loading and CDN/local fallback logic.
* `/src/utils/` — small reusable utilities only when needed.

When splitting modules, carefully update `index.html` to load the correct module entry point, for example:

```html
<script type="module" src="./src/main.js"></script>
```

Avoid multiple unordered classic script tags. Preserve execution order through ES module imports.

Do not leave duplicated logic in both `/app.js` and `/src/`. After migration, either remove `/app.js` from `index.html` or keep it only as a documented legacy file not used by the page.

## CSS and UI Requirements

Continue using **Tailwind CSS v4**.

* Preserve the existing visual style unless the task requires a UI change.
* Prefer Tailwind utility classes for layout and styling.
* Use direct CSS only for complex rendering, radar-specific effects, or styles that are impractical with utilities.
* Whenever class usage changes in HTML or JS-rendered templates, regenerate `/styles.css`.

Frontend resources required for map rendering are stored under `/static/`.

The frontend currently prioritizes static image assets from the Cloudflare R2 CDN:

```text
https://img.hoozi.net/static/
```

Preserve CDN-first behavior unless the user asks otherwise. Keep local `/static/` assets as fallback.

## Localization Requirements

At the top-level UI, the frontend supports:

* Simplified Chinese
* Traditional Chinese
* English

Whenever user-visible text changes, update all three language versions.

Do not directly machine-translate phrasing. Localize naturally for each language.

Runtime-required strings, protocol keys, API names, and code identifiers should stay in the exact format required by the software.

## Documentation Requirements

For the HOOZi 3.0 migration, create and maintain:

* `/docs/protocol/hoozi3-web-radar-protocol.md`
* `/README.md`
* `/README_CN.md`

`README.md` must be written in native English.

`README_CN.md` must be a Simplified Chinese version based on the English README, not a separate unrelated document.

The protocol document must include:

* Data source and message flow.
* Known message types or payload shapes.
* HOOZi 3.0 fields from `web_radar.lua`.
* Field meanings verified from the Lua script or API reference.
* Old HOOZi 2.0 field equivalents where applicable.
* Transformation logic.
* Unsupported or uncertain legacy fields.
* Frontend behavior affected by each field.

## Coding Conventions

JavaScript should use native ES modules.

Use `const` for bindings that are not reassigned.

Use clear, descriptive names consistent with the existing codebase.

Prefer small helper functions over large procedural blocks.

Keep protocol parsing separate from rendering logic.

Keep state normalization separate from DOM manipulation.

Do not add production dependencies without explicit user approval.

Do not commit generated or external dependency folders such as `node_modules/`.

## Tooling and Workflows

Install Tailwind CLI dependencies when needed:

```bash
npm install tailwindcss @tailwindcss/cli
```

After changing Tailwind class usage or CSS input, regenerate the compiled stylesheet:

```bash
npx @tailwindcss/cli -i ./input.css -o ./styles.css
```

Before considering the task complete, run the available project checks. If the repository has no test/lint scripts, at minimum verify:

```bash
npm install
npx @tailwindcss/cli -i ./input.css -o ./styles.css
```

Also inspect `package.json` before assuming available scripts.

## Completion Criteria

A HOOZi 3.0 migration task is not complete until:

* `index.html` loads the correct ES module entry point.
* The old monolithic `/app.js` is no longer the active frontend entry unless explicitly documented as legacy.
* HOOZi 3.0 protocol parsing is isolated in a dedicated module.
* All verified `web_radar.lua` fields are either implemented or explicitly documented as intentionally unsupported.
* `/docs/protocol/hoozi3-web-radar-protocol.md` exists and reflects the implemented behavior.
* `/README.md` and `/README_CN.md` exist and describe the HOOZi 3.0 version.
* Tailwind CSS v4 remains in use.
* `/styles.css` is regenerated when required.
* The final response summarizes changed files, verification performed, and any unresolved uncertainties.
